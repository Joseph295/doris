# 第 1 章：Doris 是什么样的系统

在打开任何一行源码之前，先回答一个更基础的问题：Doris 到底是为了解决什么而存在的。这不是市场定位问题，而是内核判断力的起点——一个系统的每一处实现细节，最终都能追溯到它当初"决定做什么、决定不做什么"这组取舍上。本章不介绍列存、MPP、OLAP 这些你早已熟悉的概念本身，而是回答：面对实时分析这个场景，Doris 在一堆成熟方案之间做了哪些具体选择，又为此放弃了什么。理解了这组取舍，后面章节里那些看似繁琐的设计（三种数据模型、两进程结构、自研存储格式）才会变成"本该如此"，而不是"莫名其妙"。

## 1.1 问题：实时分析场景到底难在哪

先把"实时分析"这个词还原成一组具体、可量化的约束。设想一个典型的实时数仓场景——上游是若干业务库和埋点流，下游同时挂着 C 端看板、运营后台和分析师的即席查询。这套系统同时被四类需求拉扯：

- **高并发点查**：运营后台按订单号、用户 ID 取明细，QPS 上千，要求 P99 在 100ms 以内。这类查询命中的行很少，但并发高、延迟敏感。
- **大宽表聚合**：分析师对一张几十列、数亿到数十亿行的宽表做多维 `GROUP BY`，扫描量大，要求秒级返回，且维度组合无法预先穷举。
- **实时写入可见**：上游 binlog / Kafka 增量以每秒数十万行的速率进来，要求写入后秒级可查——不能等小时级批处理。
- **按主键更新**：订单状态会翻转、维度会回填，CDC 场景本质是 upsert，已经写进去的行需要被就地更正，而不是不断追加历史版本让查询自己去去重。

难点不在于其中任何一条——每一条单拎出来都有成熟方案。难点在于这四条**同时成立**，而它们在存储层面天然互相拉扯。最尖锐的一对矛盾是：大宽表聚合要求列存——按列连续存放、批量扫描、高压缩比，代价是数据以不可变的大块文件（page/block）为单位组织，最小 IO 单位是一个数据页而非一行，取一行也要解压读取它所在的整个页；而实时写入 + 按主键更新要求存储是可变的、能高频接收小批量增量、能就地改写某一行，这与列存"批量、不可变、离线覆盖"的假设直接冲突。再叠加高并发点查想要的随机访问索引，一套存储结构很难同时把这几件事都做好——把点查、聚合、写入、更新各自的最优存储形态列出来，你会发现它们指向四个不同的方向。

工业界对这个矛盾的经典回避方式是 **Lambda 架构**：用一套 KV/行存系统扛点查和更新，用一套列式 OLAP 扛聚合，再用一套批处理兜底做全量修正。它能跑，但代价是把复杂度转嫁给了数据管道——同一份数据在多个系统里冗余存储，口径要人工对齐，链路延迟叠加，任何一处 schema 变更都要在几套系统里同步。运维和数据一致性的成本，最终都记在这笔"用多套系统拼一个需求"的账上。

所以问题可以精确地重述为：**能不能用一套系统、一份数据，同时满足高并发点查、大宽表实时聚合、秒级写入可见和按主键更新，且保持标准 SQL 接口和可接受的运维复杂度？** 下面几类方案，都是对这个问题的不同回答。

## 1.2 候选方案与权衡

评价一个方案不能只看它快在哪，要看它"解决了什么、又把代价转嫁到了哪里"。真诚地看，下面四类方案各自解决了问题的一部分，也各自留下了明确的短板。

**a. Hadoop 系离线数仓（Hive / Spark SQL）**

它解决的是"海量 + 复杂 ETL + 低成本"。存算天然分离，数据躺在 HDFS/对象存储上，计算按需拉起；生态完整，几乎任何数据格式和处理逻辑都能接；吞吐极大，PB 级全表扫描不在话下。

代价是延迟和访问模式。查询要经过调度排队加引擎启动开销，延迟是分钟级到小时级，天然不面向交互；没有点查能力，取一行也要扫一个分区；写入以分区批量覆盖为主，行级更新和秒级可见需要 Hive ACID 这类较重的补丁，并非它的设计初衷。它擅长的是离线加工，不是实时服务。

**b. 预计算系（Druid / Kylin）**

它解决的是"固定维度下的极低查询延迟 + 高并发"。思路是把聚合结果提前算好——Kylin 预构 Cube 落到 HBase，Druid 在摄入时做 roll-up 并建位图索引——查询直接命中预聚合结果，因此又快又抗并发，Druid 还支持实时摄入。

代价是灵活性和维度爆炸。预计算的前提是维度组合可枚举：Kylin 的 Cube 维度一多，构建时间和存储就指数膨胀；Druid 的 roll-up 会在摄入时丢掉明细，事后想查原始行很贵。更根本的是，任何超出预定义维度/度量的查询，要么不支持，要么退化成慢路径；schema 演进或口径回刷往往意味着重建 Cube。它用"提前算"换查询延迟，代价是牺牲了即席分析的灵活性。

**c. ClickHouse：单机列存的性能标杆**

它解决的是"单表大宽表聚合的峰值性能"。向量化列存打磨得很深，单表扫描聚合的单机吞吐当年少有对手；MergeTree 支持实时写入加后台合并，稀疏主键索引让范围过滤很高效。

代价（这里指 2020 年前后的状态，此后 ClickHouse 的分布式和 join 能力一直在补齐）主要在分布式和易用性：分片依赖手工配置 Distributed 表，扩缩容时数据重分布要人工搬迁；join 是弱项，分布式 join 需要数据预分布或广播，优化器不成熟，实践中常靠把数据打平成大宽表来规避；缺少标准的多副本一致性事务；SQL 是非标准方言，BI 工具和既有 SQL 资产迁移成本高。它把复杂度留在了运维和建模的心智负担上。

**d. MPP 数仓（Greenplum 类）**

它解决的是"完整标准 SQL + 分布式分析"。基于成熟的关系数据库内核（Greenplum 源自 PostgreSQL），SQL 完整、优化器成熟、分布式 join 和聚合能力齐全，还带事务语义，行列混合存储兼顾一定的点查。

代价在实时性和并发模型。它面向批量 `COPY`/ETL 设计，高频小批量写入会带来写放大和 vacuum 压力，秒级可见不是强项；基于每连接进程/会话的模型，高并发连接的开销偏大；传统 MPP 存算耦合，扩容要做数据 redistribute。它把 SQL 完整性和事务做扎实了，但实时写入这一环偏弱。

把四类摆在一起看：Hadoop 有吞吐无实时与点查，预计算有速度无灵活，ClickHouse 有单机峰值无分布式易用性，MPP 有完整 SQL 无实时写入。没有一类同时踩中 1.1 里那四个需求——这正是 Doris 要挤进去的缝隙。

## 1.3 Doris 的取舍

Doris 的答案不是发明新范式，而是在上述成熟技术里做一组有针对性的组合，并接受相应的放弃。可以把它的核心选择逐条对回 1.1 的痛点：

- **MPP 架构**：解决大宽表聚合的分布式扫描与分布式 join（对应查询 B），同时补上 ClickHouse 当年欠缺的分布式短板，并保留 MPP 数仓那套完整标准 SQL 与优化器（吸收方案 d 的长处）。
- **列存 + 向量化执行**：解决聚合扫描的效率问题（查询 B），这是与 ClickHouse 同源的选择。
- **自研存储引擎**：这是 Doris 最关键、也最容易被忽视的取舍。它没有直接复用 HDFS+Parquet（不可变、不支持行级更新）或 RocksDB（KV、不擅长列式扫描），而是自研一套 Rowset/Segment 列式格式，并在其上做三种数据模型——明细（Duplicate）、主键（Unique）、聚合（Aggregate）。增量以 MemTable + 小 Rowset 的形式写入、写完即可查，解决实时可见（写入需求）；Unique/主键模型支持 upsert，解决按主键更新（更新需求）；前缀索引等结构支撑短路点查，让高并发点查（查询 A）虽不及专用 KV 但足够用。**一句话：自研存储的理由，正是市面上没有一种现成格式能同时满足列存扫描 + 实时增量可见 + 行级更新 + 点查索引这四件事。** 1.1 里那对最尖锐的矛盾，就是在这一层被硬啃下来的。
- **MySQL 协议兼容**：解决接入与生态成本（针对方案 c 的方言短板），BI 工具、连接池、JDBC/ODBC 驱动、既有 SQL 资产可以直接复用，迁移摩擦最小。这是一个成本收益极不对称的选择——实现一层协议兼容的工程量有限，换来的是整个 MySQL 生态的即插即用。
- **FE（Java）/ BE（C++）前后端分离的两进程模型**：FE 负责解析、优化、元数据与事务协调——这一层逻辑复杂、迭代频繁，Java 生态在开发效率和复杂状态管理上有优势；BE 负责向量化执行与存储——这一层贴近硬件、对内存和延迟敏感，C++ 无 GC 停顿、能精细控内存。用语言边界切分职责边界，是一个刻意的工程取舍，代价是跨进程通信和序列化开销（后面会看到 thrift/protobuf 契约就是为此存在）。

需要点明的是，这里没有哪一项是 Doris 独创的技术：MPP 来自传统数仓，向量化列存与 ClickHouse 同源，MySQL 协议是现成的。Doris 的判断力体现在**组合**上——它没有在任何单一维度追求单点最优，而是让这几项互补，共同覆盖 1.1 那四个互相拉扯的需求。真正需要从零啃下来的，是那套要同时兼顾列存扫描、实时增量、行级更新和点查的自研存储引擎，因为这一块确实没有现成答案可抄。

有得必有舍。Doris 明确放弃的，同样构成它的定位：

- **不做 OLTP**。没有面向单行的高频事务、行锁、可串行化隔离。导入走的是批量事务（2PC + Label），单条 `INSERT` 也要走同样偏重的事务路径，高频单行写会让小 Rowset 泛滥、把压力转嫁给后台 Compaction。想把它当业务库用，方向就错了。
- **单行/交互式事务能力有限**。没有 `BEGIN` 起、多语句交叉读写、按语句回滚那套完整事务语义；`UPDATE`/`DELETE` 本质是批量重写而非就地原地更新，适合数据订正，不适合承接联机交易。
- **放弃了预聚合的延迟下限**。相比 Kylin/Druid 把结果提前算好，Doris 默认是运行时聚合，用物化视图/Rollup 部分弥补，但不追求"任意固定维度查询都毫秒返回"这条下限。
- **放弃了单机峰值的一部分**。相比 ClickHouse 的单机峰值性能，Doris 为分布式一致性、多副本、元数据协调付出了额外开销，换来的是扩缩容与运维上的易用性。

看清"放弃了什么"，比记住"支持什么"更能划清 Doris 的适用边界：它是实时分析型数据库，不是事务型业务库，也不是离线批处理引擎。

## 1.4 从取舍到代码：顶层结构印证

上面这些取舍，不用等到读完全书，在仓库的顶层目录结构里就能找到第一重印证。这里只做概览级的"目录—职责"映射，不深入代码；每条都对应 1.3 的一个选择。

**`fe/` —— Java 编写的分析与元数据层。** 对应"完整 SQL + 优化器"和 FE 的职责边界。查询优化器在 `fe/fe-core/src/main/java/org/apache/doris/nereids`（Nereids，第二部分会专章拆解），元数据体系在 `fe/fe-core/src/main/java/org/apache/doris/catalog`，进程入口是 `fe/fe-core/src/main/java/org/apache/doris/DorisFE.java`。选 Java 承载这一层，正是因为解析、优化、元数据这类逻辑复杂、演进快。

**`be/` —— C++ 编写的向量化执行 + 存储层。** 对应"MPP 并行执行 + 列存 + 自研存储引擎"。Pipeline 执行调度在 `be/src/exec/pipeline`（pipeline 引擎的存在本身就是 MPP 并行执行的落点），向量化的数据结构 Block/Column/DataType 在 `be/src/core`，自研存储引擎在 `be/src/storage`，进程入口是 `be/src/service/doris_main.cpp`。选 C++ 承载这一层，是为了贴近硬件、避免 GC 停顿、精细控内存。

**`gensrc/` —— FE 与 BE 之间的契约层。** 两进程模型必然需要一套跨语言的接口定义，这就是 `gensrc/` 的意义。`gensrc/proto/` 放 protobuf 定义，比如三种数据模型的枚举 `KeysType`（`DUP_KEYS`/`UNIQUE_KEYS`/`AGG_KEYS`）就定义在 `gensrc/proto/olap_file.proto`；`gensrc/thrift/` 放 thrift 定义，FE 与 BE 之间的 RPC 接口（如 `gensrc/thrift/FrontendService.thrift`、`gensrc/thrift/BackendService.thrift`）都在这里。FE 的 Java 代码和 BE 的 C++ 代码从这套定义分别生成桩，这就是 1.3 里"两进程模型"的物理边界。

三个顶层目录，恰好对应"Java 分析层 / C++ 执行存储层 / 二者之间的契约"这条主线。后面所有章节，无非是在这三块地基上继续往下挖。

## 1.5 本章小结与自查问题

本章不讲 Doris 是什么，讲的是 Doris 为什么是现在这个样子。核心结论：实时分析的难点在于高并发点查、大宽表实时聚合、秒级写入可见、按主键更新这四件事要用一套系统一份数据同时满足，而它们在存储层天然互相拉扯；四类既有方案各解决一部分、各留一处短板；Doris 的选择是 MPP + 列存向量化 + 自研存储引擎 + MySQL 协议 + FE/BE 两进程，代价是放弃 OLTP 事务与预聚合延迟下限，把自己定位成实时分析型数据库。这组取舍，在 `fe/`、`be/`、`gensrc/` 的顶层结构里就能读出第一重印证。

读完本章，检验一下自己是否真的读进去了：

1. 为什么 Doris 不直接用 HDFS+Parquet 或 RocksDB 做存储，非要自研一套存储引擎？（提示：把 1.1 那四个需求叠加到同一份数据上，现成格式各缺哪一块？）
2. 为什么选 FE Java + BE C++ 的双语言、双进程结构？两种语言各自被放在哪一层，分别是看中了什么？
3. Doris 明确放弃了哪些能力？如果一个业务需要高频单行事务更新，为什么不该选 Doris——具体会在存储和事务路径上付出什么代价？
4. 同样是向量化列存，当年 Doris 相对 ClickHouse 的核心差异在哪几点？各自的取舍代价是什么？
5. 1.1 里"四个需求同时存在"的矛盾，落到存储层面，最难调和的是哪两个需求？（提示：一个要求批量不可变，一个要求行级实时可改。）

下一章《三大件解剖》会把 FE / BE / MetaService 三个进程的职责边界、进程内部结构和它们之间的协作关系逐一拆开——本章画出的顶层目录地图，会在那里变成可运行、可调试的进程模型。
